# Inside a 14.5M Ops/sec C++ Order Book Matching Engine

three versions into this project, i made one part of it ten percent slower. not on purpose, but once i understood why it happened, i kept the number and wrote up the explanation instead of quietly fixing it before anyone saw the regression. this is the story of everything that led up to that decision, starting from a much earlier and much dumber bug.

what got built: a limit order book, from scratch, in c++20. price-time priority matching, partial fills, market orders. no external order-book library, no framework doing the actual matching underneath it — the whole thing, top to bottom, is code i wrote and then spent a long time trying to prove wrong. by the end it's doing up to 14.5 million of those matches a second, on ordinary laptop hardware, with a full paper trail proving the number is real. that's the destination. this is the route there, including the parts where it got worse before it got better.

it mostly held up. the two places it didn't are worth more than the parts that worked first try.

grab a coffee, this is a long one.

---

## what this thing actually does

an exchange, underneath all the ui and the api and the marketing, is a matching engine deciding what an incoming order trades against, at what price, in what sequence. get the logic wrong and someone loses money on a trade that should never have happened. get it slow and someone else's order gets there first.

i picked this as a project for a specific reason: it's small enough to hold completely in your head — no sprawling service mesh, no auth, no schema debates — but deep enough that "correct" and "fast" genuinely fight each other the moment you start caring about both. you can't fake your way through it by knowing a framework well. you either understand price-time priority or your test suite tells on you immediately.

one rule going in, and i stuck to it harder than i expected to need to: depth over breadth. it would've been easy to bolt on multiple symbols, a rest api, ten order types, a live web dashboard, and have every one of those things be shallow. i wanted one thing taken as far as i could actually take it. single instrument, single thread, limit and market orders, nothing persisted, nothing networked — all of it in service of one question, answered as thoroughly as i could manage: what actually makes an order book fast, and how do you *prove* it instead of just claiming it.

## three classes, no inheritance

```cpp
class MatchingEngine {
    OrderBook book_;
};

class OrderBook {
    std::map<Price, PriceLevel, std::greater<Price>> bids_;
    std::map<Price, PriceLevel, std::less<Price>> asks_;
    std::unordered_map<OrderId, OrderLocation> orderLocations_;
};

class PriceLevel {
    std::list<Order> orders_;
    Quantity totalQuantity_;
};
```

`MatchingEngine` owns one `OrderBook`. `OrderBook` keeps two maps of price levels, bids sorted highest-first and asks sorted lowest-first, so the best price is always sitting at `begin()`. each price level holds a list of the resting orders at that price, oldest first — that ordering *is* the "time" half of price-time priority.

worth being precise about what `std::map` actually is, since it comes up again later: it's not a flat sorted array, it's a tree — every insert, lookup, and "give me the smallest key" walks down a small number of branches from the root instead of scanning a list. that's what keeps it sorted cheaply as things come and go. it's also where its cost comes from, and that cost is the entire subject of a later section.

nothing here is virtual. i considered a polymorphic `Order` hierarchy — `LimitOrder`, `MarketOrder`, a virtual `match()` — for about as long as it took to remember two things about what that actually costs.

first: a normal function call jumps to a fixed address baked in at compile time, so the cpu can prefetch and start working on what comes next before the call even finishes. a *virtual* call — the whole point of `LimitOrder`/`MarketOrder` overriding a shared `match()` — doesn't know which function it's calling until runtime, so it has to load the real address out of a hidden per-object table first, then jump to whatever that turned out to be. that's an indirect jump, and the cpu's branch predictor — the part that guesses which way a branch or call is going before it's actually resolved, so it can keep working ahead instead of sitting idle — is measurably worse at guessing those than it is at a plain, fixed-address call. every one of those is a small chance of the cpu guessing wrong and throwing away the work it started speculatively, which is exactly the kind of cost this whole project keeps chasing back to its source.

second: `LimitOrder` and `MarketOrder` would be different sizes in memory, and a container like `std::list<Order>` needs to know the size of what it's storing up front. so polymorphic orders can't sit in the list by value the way a plain struct can — they'd need to live behind pointers instead, one more indirection, one more place to chase through memory instead of reading it directly.

so `Order` stays a flat struct, and the field that would only apply to limit orders gets a comment explaining itself instead of its own subclass:

```cpp
struct Order {
    OrderId id;
    Price price;      // irrelevant for Market orders, but included to avoid polymorphism
    Quantity quantity;
    Side side;
    OrderType type;
};
```

the one genuinely clever bit is cancellation. finding an order to cancel by scanning every price level is O(n) — cost grows in a straight line with however many orders are resting — which falls apart the moment cancels are common, and in real markets they're extremely common. the fix is a hash map from `OrderId` straight to *where that order lives*: which side, which price, and a `std::list<Order>::iterator` pointing directly at it. a hash map's whole trick is turning the key itself into (roughly) the answer to "where do i look": run the id through a hash function, land close to the right slot directly, no scanning required — that's what makes it O(1), a small, roughly constant amount of work no matter how many orders are resting. `std::list` is the one standard container that guarantees an iterator survives insertions and deletions happening anywhere else in the list. cancel becomes a hash lookup and an erase at a known position. no traversal, nothing to invalidate.

## the rule the whole thing exists to enforce

two kinds of order, and the difference matters for everything below. a limit order says "trade at this price or better, and if you can't right now, wait" — it's willing to rest on the book. a market order says "trade right now, at whatever price is actually available" — it never rests, it either matches immediately or the unfilled part just gets thrown away.

an incoming order sweeps the opposite side of the book — a buy against asks, a sell against bids — starting from the best price, until it's either fully filled or can't match anymore. every trade happens at the *resting* order's price, never the incoming order's, because the resting order got there first and that's what "priority" means.

```cpp
while (orderIt != orders.end() && order.quantity > 0) {
    Order& restingOrder = *orderIt;
    Quantity tradeQty = std::min(order.quantity, restingOrder.quantity);

    trades.emplace_back(restingOrder.id, order.id, restingOrder.price, tradeQty);
    order.quantity -= tradeQty;
    restingOrder.quantity -= tradeQty;

    if (restingOrder.quantity == 0) {
        orderIt = orders.erase(orderIt);
    } else {
        break;
    }
}
```

that `break` looks almost decorative until you actually trace why it's there. `tradeQty` is the smaller of the two remaining quantities, so after subtracting it, at least one side is now at zero. if it wasn't the resting order, it has to be the incoming one — which means the surrounding loop's own condition is about to end it anyway. the `break` isn't strictly required for the code to behave correctly. it's there to say the invariant out loud, in the place it's true, instead of leaving it to be re-derived by whoever next has a reason to touch this function and doesn't happen to rediscover the same reasoning i just did.

market orders run the identical loop with no price limit at all, and whatever doesn't fill gets thrown away rather than left resting. this logic used to exist as four separate, nearly-identical functions — one each for limit-buy, limit-sell, market-buy, market-sell — before i collapsed them into one, parameterized on side and an optional limit price. that wasn't really a speed decision. it was a "four copies of the same twenty lines is four places the same bug can hide" decision.

## a benchmark that was lying to me

before optimizing anything i needed a number i actually trusted, and getting one turned out to be less obvious than i expected.

three workloads, each leaning on a different part of the system: orders scattered across a wide price range (stresses price-level lookup), a 70/30 mix of inserts and cancels (stresses the cancellation path under churn), and every single order landing at the exact same price (removes price-level lookup entirely, stresses the linked-list append at one very deep level).

and a warm-up pass first — ten percent of the workload, run and discarded before any timer starts. two things need to be "warm" before a number means anything: the instruction cache, a small pool of very fast on-chip memory that holds whatever code just ran so the cpu doesn't have to fetch it from slower main memory again — and the branch predictor from a section ago, which gets better at guessing this specific code's branches the more it's actually seen them run. both start cold, guessing worse and fetching more from slow memory, the first time any code path executes. a benchmark that starts timing on action one is partly timing that warm-up cost, not the steady-state speed anyone actually cares about.

the part that actually bit me: my first version of this harness measured throughput and per-operation latency in the same pass, timing every individual operation while also totaling up a batch time. `std::chrono::high_resolution_clock` is not free — 20 to 40 nanoseconds of overhead per call is a reasonable estimate, since reading it means asking the operating system (or a dedicated hardware timer register) what time it is right now, which is itself a small piece of work, not a free instruction — and calling it twice per operation while trying to measure aggregate throughput meant the throughput number was partly measuring its own stopwatch. i caught it because the numbers looked off against the separately-measured latency figures, not because i'd reasoned my way to the bug in advance. fixed by splitting it into two completely separate passes: one timer wrapping the whole batch with zero per-operation instrumentation inside it, and a second pass on a fresh engine, replaying the identical sequence, timing every operation individually for the percentile numbers. every throughput figure anywhere in this project comes from a pass that never touches `std::chrono` until it's entirely finished.

## two bugs, both at the same door

the engine worked. every test passed — exact matches, partial fills, price ordering, cancellations, the market-order sweep. i had numbers i believed in and a methodology built specifically to make sure i could believe them.

so i turned around and audited the whole thing as if it belonged to someone whose work i didn't trust yet. found two real bugs, and both of them were sitting at the exact same kind of door: the point where something from outside the program gets let in.

**the first** was in `OrderBook::addOrder`, which had no guard against a reused `OrderId`. insert an order whose id already belongs to something resting in the book, and the cancel index — the hash map from a few sections back — just overwrites its old entry. the original order stays physically in the book, still tradeable, but it's no longer reachable by id. cancel that id later and you cancel the *new* order instead, and the original can never be touched again. no exception. no crash. nothing in any output that looks wrong. the book just quietly starts lying about one specific order, forever.

this isn't an edge case you'd have to go looking for either — a client retrying after a dropped acknowledgment, a corrupted replay file, an id generator with an off-by-one somewhere upstream, all produce exactly this.

**the second** i genuinely didn't believe until i reproduced it myself. the csv replay parser fed price and quantity fields straight into `std::stoull`. `std::stoull("-5")` does not throw. it accepts the minus sign and hands back the two's-complement wraparound instead — `18446744073709551611` — and i wrote a standalone five-line program purely to watch that number appear on my own screen, because it felt like something i had to be misremembering. i wasn't. the reason it's specifically *that* number and not just some generic garbage value: computers store negative numbers by counting backwards from the top of however many bits they have — "two's complement" is the name for that scheme — so asking an *unsigned* type (one that was never expecting a sign in the first place) to interpret "-5" hands back whatever bit pattern -5 would have been in a signed number, reinterpreted as a huge positive one instead. a negative price in a malformed row silently becomes a near-maximum `uint64_t` price instead of a parse error.

both fixes share the same shape — reject loudly, instead of accepting quietly:

```cpp
// OrderBook::addOrder — refuse the collision instead of overwriting it
if (orderLocations_.find(order.id) != orderLocations_.end()) {
    return false;
}
```

```cpp
// CSVParser — the sign gets checked before stoull ever runs
if (firstNonSpace != std::string::npos && token[firstNonSpace] == '-') {
    throw std::runtime_error(std::string(fieldName) + " must not be negative: '" + token + "'");
}
```

and then a fuzz test built specifically to make the first bug reproducible on demand: 20,000 randomized insert/cancel operations, roughly one in ten inserts deliberately reusing a live id, checking the book's invariants after every single one — every price level's tracked quantity matches its actual resting orders, no id shows up twice. that test is what should have caught this in the first place, and now it would, months before an audit thought to go looking.

## a pipeline that only checked one thing

before the audit, ci here was one job: build in debug with address and undefined-behavior sanitizers on, run the tests, done. sanitizers are worth being specific about, since they come up again later: they're a special build mode that adds extra checks around every memory access and every operation the c++ standard leaves technically undefined, so a bug that would normally just silently corrupt something or produce a wrong-but-plausible answer instead crashes immediately, at the exact line that caused it, with a diagnostic. without one, a use of memory that's already been freed might work fine ninety-nine times out of a hundred and then fail somewhere completely unrelated, days later, in a way that's nearly impossible to trace back. which sounds reasonable until you notice everything the pipeline didn't cover. the benchmark binary — the thing every published number in this project comes from — had never been built by ci at all. the release configuration, `-O3` — the flag that tells the compiler to spend extra time aggressively rewriting the code for speed (inlining functions, unrolling loops, reordering things the debug build leaves alone) — the actual flags those numbers were measured under, had never been confirmed to even *compile* on a clean checkout. an optimized build isn't just a faster version of the debug build; the compiler is generating meaningfully different code, which occasionally means a bug that only shows up in one configuration and not the other. there was no static analysis, no formatting check, no coverage number. "the tests pass" and "the code is clean" were both things i was just asserting, not things anything was verifying.

five jobs now, instead of one. the original debug-plus-sanitizers job stayed, but now it also builds and smoke-tests the benchmark binary — not trusting its numbers, just confirming it runs against a real csv file without crashing or throwing. a second job rebuilds everything in release mode and re-runs the full suite there too, since debug and `-O3` are different enough compilers-under-the-hood that "it works in debug" isn't the same claim as "it works in the configuration that produced the readme's numbers." a formatting check runs `clang-format` in dry-run mode and fails the build on any diff — deliberately the one blocking check among the new ones, since a formatting rule that doesn't actually block anything just trains people to ignore it. static analysis runs `clang-tidy`, but *not* blocking, on purpose: the tool had literally never run against this codebase before, and turning on a strict gate against a pile of findings nobody's triaged yet is how you teach a team to dismiss every red x without reading it. and a coverage job runs the suite under instrumentation and prints a real percentage into the build log instead of leaving "well-tested" as a vibe.

that non-blocking decision on static analysis turned out to matter in a very literal way months later, when this got pushed to a real github runner for the first time. two things had been sitting as open questions the whole time this lived on one machine: whether `clang-tidy` would find anything once it actually ran, and whether the sanitizer job would even complete — my own mac's clang has a specific, unrelated quirk where address sanitizer hangs forever on any thrown exception, which meant i'd only ever verified correctness locally through the undefined-behavior sanitizer alone, never the full combination the actual ci job runs. both came back clean on the very first real push. small thing, but it's the kind of "i don't actually know yet" that's easy to quietly round up to "probably fine" instead of writing down and then just... checking, once the chance to check for real showed up.

## a paper trail for decisions, not just code

somewhere around the point where i started planning the performance work that fills most of the rest of this post, i started keeping a different kind of file: one dated, numbered document per decision, no matter how small. not "here's what the code does" — that's what the code is for — but "here's what else was on the table, and why it lost." twenty-plus of these exist now. a decision to use a fixed-capacity pool instead of a growable one has its own file. so does the decision to keep `clang-tidy` non-blocking. so does the choice to profile with apple's own tooling instead of reaching for a linux vm.

the rule i set for myself was: never edit an old entry to reflect a later change of mind. if a later version does something differently, that's a new, separately-dated file, with one line added to the old one pointing forward. the point is that "what we believed at the time, and why" is worth keeping around exactly as it was believed, not silently smoothed over once it turns out to be incomplete.

that rule got tested for real when i found a factual error, not a change of mind, sitting in one of these files: an environment string that said one macos version when the machine had actually been running a different one the whole time, for reasons that had nothing to do with any engineering decision — it was just wrong, copy-pasted from an earlier entry without checking. my first instinct was to leave the old entries alone out of respect for the "don't edit history" rule and only fix the one i'd personally just written. that's the wrong call, and it took someone else pointing it out for me to see it clearly: the "don't edit" rule exists to protect *decisions and the reasoning behind them*, not to protect a plain mistake nobody ever actually verified. i went back, checked this exact machine's own update history to get real evidence of what had actually been installed and when, and fixed every row that was wrong — not just the one i'd introduced. a rule that can't tell the difference between "we used to believe X, and later learned Y" and "someone typo'd a version number" isn't actually protecting anything worth protecting.

## why four order books instead of one fast one

correctness was in a place i actually trusted now — not "the tests pass" trusted, but "i went looking for ways to break it and mostly couldn't" trusted. the obvious next move was performance, and the obvious wrong way to chase it would have been picking one "optimized" version, swapping it in, and reporting a single before/after number.

what i did instead: build several implementations of the same book, each one changing exactly one thing from the last, and require every new one to be *provably identical in behavior* to the original before its speed counts for anything. slower to build. also the only version of this where "removing heap allocation made it 34% faster" is a measured fact instead of one anecdote from one binary.

the architecture made this cheap, which is the actual payoff of avoiding inheritance three sections ago — `MatchingEngine` became a template. a template in c++ is a function or class written once with a placeholder type in it, and the compiler generates a real, fully-typed version of it for every actual type you use it with — so `MatchingEngineT<BookT>` isn't one engine that works with anything, it's a stamp the compiler presses out separately for each book implementation, at compile time, with zero runtime cost for the flexibility. any book exposing the same handful of methods can be swapped in with nothing else in the codebase changing. and a differential test harness runs the identical random action sequence through two implementations side by side and demands the resulting trade ledgers match exactly:

```cpp
template <typename BookT, typename... Args>
std::vector<Trade> runLedger(const std::vector<Action>& actions, Args&&... args) {
    MatchingEngineT<BookT> engine(std::forward<Args>(args)...);
    std::vector<Trade> ledger;
    for (const auto& action : actions) {
        if (action.kind == Action::Kind::Insert) {
            auto trades = engine.processOrder(action.order);
            ledger.insert(ledger.end(), trades.begin(), trades.end());
        } else {
            engine.cancelOrder(action.order.id);
        }
    }
    return ledger;
}
```

the template part is just `BookT` — whichever book implementation gets plugged in — and `Args`, a placeholder for "however many constructor arguments that specific book needs" (some need none, some need a price range, one needs both a price range and an id limit), forwarded straight through unchanged. strip the template machinery away and it's a plain loop: build an engine, replay every action against it in order, collect every trade it produces into one list, hand that list back. run that exact loop twice, once per book implementation, on the exact same `actions`, and the two returned lists have to match, trade for trade.

a faster implementation that's quietly wrong isn't worth having. this is what would catch that, before a single benchmark number gets written down anywhere.

## version two: nothing asks malloc for anything anymore

the baseline stores resting orders in `std::list<Order>` — one heap allocation per order, and pointer-chasing through separately-allocated nodes every time you walk the list. two things worth actually unpacking there, since they explain a whole version of this project.

the heap is the pool of memory a program asks the operating system for at runtime, for anything whose size or lifetime isn't known up front — as opposed to the stack, which is fast precisely because it only ever hands out and reclaims memory in strict last-in-first-out order, no bookkeeping required. `malloc` is the function that actually asks for a heap allocation, and it's not free: the allocator has to find a free block the right size, update its own internal bookkeeping to remember what's now taken, and do all of that in a way that's safe if the program is multi-threaded, even when this one isn't. every one of those steps is real cpu work that happens before the "useful" work of storing an order even starts.

then there's pointer-chasing: `std::list`'s nodes are each their own separate heap allocation, so walking the list means following a chain of pointers to wherever the allocator happened to put each one — which is not next to each other in memory, and not predictable. every hop is a real chance the cpu has to stop and wait for main memory instead of finding what it needs already sitting in a fast on-chip cache, because nothing about "the next node" told it in advance where to look.

version two changes only that. price levels stay `std::map`, unchanged, same lookup cost as before — isolate one variable, same discipline as everywhere else in this project.

the replacement is an intrusive doubly-linked list, where the `prev`/`next` pointers live inside the node itself rather than in a separate container, backed by a pool that hands out fixed slots instead of calling `malloc`:

```cpp
uint32_t acquire(const Order& order) {
    uint32_t index;
    if (!freeList_.empty()) {
        index = freeList_.back();
        freeList_.pop_back();
    } else if (highWaterMark_ < capacity_) {
        index = highWaterMark_++;
    } else {
        throw std::runtime_error("OrderPool: capacity exhausted");
    }
    nodes_[index].order = order;
    return index;
}
```

one decision here needs explaining, because the tempting alternative is wrong for a reason that only becomes obvious once you think about what a pool is actually protecting you from. this pool has a fixed capacity, decided up front, and exhaustion is a hard error rather than an automatic grow. a pool that can silently grow means an allocation event at some unpredictable moment — and the moment a pool actually runs out is precisely when the book is under the most load, which is the single worst possible time to introduce a latency spike. letting it grow quietly defeats the entire reason to have a pool. size it deliberately for the workload you expect, and if that guess turns out wrong, find out immediately and loudly, not as an unexplained spike three months from now.

this is also exactly the kind of manual lifetime management where a use-after-free likes to hide — code that keeps using a slot in the pool after it's already been handed back and possibly reused for a completely different order, reading or writing data that isn't what you think it is anymore — so i didn't just run it once and move on. the differential test against a 200,000-action random workload passed on the first attempt. so did a second one built specifically around the all-same-price scenario, since that's where an intrusive list and a plain `std::list` diverge internally the most. still not satisfied, i ran a standalone 500,000-action stress pass under undefined-behavior sanitizer instrumentation on top of all that. also clean.

**the number**: throughput up 33 to 35 percent, consistently, across every workload, with identical trade counts to the baseline every time.

getting real hardware evidence behind that number turned into its own detour. this machine didn't have xcode installed — just the command-line tools, enough for a compiler but nothing that profiles. installed xcode with only the macos components checked (skipped every mobile platform, none of it relevant to profiling a command-line binary, and disk space was tight). pointed the system at it. tried to record a hardware-counter trace, and the target process launched and then did nothing — zero cpu usage, no error, for several minutes straight.

the actual blocker was developer mode, disabled at the os level, silently refusing the profiler the access it needed. one command fixed it once i thought to check. none of the three things standing in the way — no xcode, the system still pointed at the wrong toolchain, developer mode off — failed with a message that pointed at itself. each one just quietly didn't work until the next thing got tried.

worth the detour: every hardware category the profiler reports dropped, in every workload — cycles spent (the basic unit of cpu time, everything measured in how many clock ticks it took), front-end stalls (time spent waiting to even fetch and decode the next instruction), speculative work thrown away (the branch predictor guessing wrong and the cpu having to discard whatever it started doing on that wrong guess), and back-end stalls (the part that actually executes instructions sitting idle, usually waiting on memory). removing heap allocation didn't save time in one isolated place. it measurably reduced cost across the entire pipeline, which is the kind of thing people say about allocation and cache locality all the time, except now i had a number attached to the claim instead of just repeating it.

what it didn't do: touch the gap between the random-price workload and the same-price one. that ratio — same-price throughput divided by random-price throughput — had been sitting at 1.668 in the baseline measurement, and measured again fresh alongside version two, it came back at 1.655. close enough to trust as "essentially the same," not close enough to pretend it's the identical number — this machine has real background load and re-measuring never gives you the exact same figure twice, which is itself worth saying plainly rather than rounding away. the standing theory — that `std::map`'s tree traversal explained why one workload consistently beat the other — hadn't been tested by this change at all. allocation was real, worth roughly a third of total runtime. it just wasn't the answer to that particular question.

## version three: the array that made one thing worse

so: replace `std::map<Price, PriceLevel>` itself, same intrusive-list order storage carried forward unchanged from version two.

the replacement is a flat array, indexed directly by price, with a bitmap tracking which prices currently have at least one resting order:

```cpp
size_t nextOccupiedFrom(size_t from) const {
    size_t wordIdx = from / 64;
    uint64_t word = occupancy[wordIdx] & (~0ULL << (from % 64));
    while (true) {
        if (word != 0) {
            return wordIdx * 64 + std::countr_zero(word);
        }
        if (++wordIdx >= occupancy.size()) return levels.size();
        word = occupancy[wordIdx];
    }
}
```

`std::countr_zero` — count trailing zeros — is a c++20 standard library function that maps to a single hardware instruction on nearly every modern cpu. instead of checking price levels for occupancy one at a time, this checks sixty-four of them per comparison and jumps straight to the first one that's actually there.

worth actually reading that code once, since it's the least self-explanatory snippet in this whole post. the bitmap is a plain array of 64-bit integers, and every price level gets exactly one bit somewhere in it — bit *n* is 1 if price level *n* currently has a resting order, 0 if it doesn't. `wordIdx = from / 64` picks out which 64-bit chunk ("word") the price we're starting from actually lives in, since 64 price levels share every one number. the line right after it — `occupancy[wordIdx] & (~0ULL << (from % 64))` — takes that word and masks off every bit *before* our starting position, so what's left only has 1s where a price level is both occupied *and* at or past where we're looking. if that's nonzero, `countr_zero` finds the lowest set bit directly — the nearest occupied price level — without a loop. if it's zero, nothing in this word qualifies, so the loop moves to the next word and repeats. sixty-four price levels get checked as a single number comparison instead of sixty-four separate ones.

a flat array needs something `std::map` never asked for, though: bounds. every incoming price has to sit inside a range decided at construction, or it gets rejected outright. i went back and forth on whether that was a real design decision or a compromise i was quietly excusing, and landed on the former — real exchanges enforce price bands and circuit breakers for entirely different, risk-management reasons, so a bounded price range isn't a toy simplification unique to this project. it's a constraint real systems already live with, for reasons that happen to line up.

here's the part i want to actually sit with instead of skipping past: random prices improved 23.7% on top of version two, heavy cancels improved 24.2%, and the same-price workload got **10.3% slower.** not noise — checked it twice, and the hardware counters agreed directly: cycles up 8.6%, and the category tied to speculative-execution waste up 4.7%, specifically and only for that one workload. everything else improved in every category. this one got worse in two of them.

the why turned out to be findable, and better than i expected once i actually looked instead of shrugging at it. that bitmap scan always starts from the array's edge — never from a cached "here's where the best price was a moment ago." with random prices or heavy churn, a lot of different price levels are occupied at once, so the scan almost always finds something within the first word or two — high density, short scan, close to free. the same-price workload has exactly one occupied price, ever, sitting near the middle of the configured range. every single order pays the full scan from the edge just to reach it, a cost `std::map` genuinely never charged, because a tree holding one entry is fast no matter where that entry theoretically sits.

and this is the part that made the regression worth reporting instead of quietly patching: the ratio between the same-price and random-price throughput — 1.668 at the very first measurement, 1.655 after version two, still sitting at 1.650 measured fresh again right before this change — dropped to **1.195** with this change. the theory that had been sitting untested since the earliest baseline finally had real evidence behind it. it just didn't resolve the way i would have guessed going in. not "random prices alone catches up while the other workload holds steady" — both numbers moved, one up and one down, landing closer together than either side moving alone would explain. i only know that shape is wrong because i measured it instead of predicting it and stopping there.

the fix is one i already know: cache the current best price instead of re-scanning from the edge every time, and only re-scan once that cached price actually empties. i'm fairly confident it closes most of the regression above without costing the workloads that already improved anything. it's deliberately not built yet, so this version's real, as-shipped cost got written down honestly first, instead of getting quietly smoothed over before anyone else saw it.

## version four: closing the loop i left open on purpose

two changes, one version, because both of them are really the same idea wearing different clothes: stop treating a bounded, well-behaved domain like it needs a general-purpose data structure to handle it.

the first change is the fix i already promised — a cached best price per side, updated the instant a price level goes from empty to occupied or back again, instead of re-derived by scanning from the array's edge on every single incoming order. the update itself is almost embarrassingly small:

```cpp
void noteInserted(size_t tick) {
    if (bestTick == kNoTick || (isBid ? tick > bestTick : tick < bestTick)) {
        bestTick = tick;
    }
}
```

one comparison, only run at the moment a price level actually starts existing. the other half — figuring out the *new* best price after the old one empties out — only has to run when the price that just emptied was the cached one, which in practice is rare. the expensive bitmap scan from version three doesn't go away. it just stops running on every order and starts running only when it's actually needed.

the second change had been sitting in every version so far without anyone questioning it: the id-to-location cancellation index was still a `std::unordered_map`, since the very first line of code. a hash, a bucket walk, on every insert and every cancel. the same bounded-domain argument that justified the price array applies here too — a real exchange hands out order ids as a dense, increasing sequence from a gateway, not scattered randomly across the entire 64-bit space. so the hash map becomes a flat array, indexed directly by id, sized once at construction, exactly the same shape of decision as the price array two sections ago.

writing the two changes was the fast part. sizing the id capacity for the benchmark was where i actually tripped: the first run threw an exception almost immediately, complaining an id was one past the array's configured bound. i'd sized it for one workload's worth of ids, forgetting the benchmark reuses the *same* id counter across all three synthetic workloads back to back, so by the time the third one starts, ids are already past double what i'd budgeted for. a bounded-domain design is only as safe as correctly reasoning about what the bound actually is — sizing it generously isn't the same thing as sizing it correctly, and this was a small, cheap reminder of that before it became an expensive one.

the differential tests passed on the first real attempt, including the one built specifically to hammer the new cache — every order at one fixed price, so the best-price tick gets set exactly once and then should never need to move again for the rest of the run. that's precisely where an off-by-one in "only re-scan if the price that just emptied was the cached one" would show up as a wrong trade instead of just a slow one. it didn't.

the number, and i checked it twice because it looked too good the first time: every workload roughly doubled on top of version three. random prices, up over double — the single largest gain of the three, for the record, since it's not the one with the better story. heavy cancels, up over double. and the same-price workload — the one that got measurably *worse* in the last section — didn't just recover, it swung the hardest of any of them: a real regression into a +100.6% gain, the biggest reversal in the whole study even if random prices' raw number edges it out. the regression i wrote up honestly instead of quietly patching became, one version later, one of the best results in the whole study.

the hardware counters backed up the mechanism directly: the same category from version three — branch-misprediction cost, what i called "speculative-execution waste" a section ago, the cpu guessing wrong and discarding the work — the one that got worse specifically on the same-price workload last time, dropped by more than half on that exact workload this time. that's the scan-from-the-edge cost actually leaving the hot path, visible on the chip, not just in the wall-clock number.

it wasn't a clean sweep on the surface, and i want to say that as plainly as i said the regression two sections ago. a different bottleneck category — the one tied to the processor waiting on data it needs before it can keep going — went *up*, in percentage terms, on every workload, most on the cancel-heavy one. first instinct was to suspect the obvious-sounding culprit: the id-indexed array is sized to every id the benchmark could ever hand out across all three workloads combined, since they share one counter, which is a much bigger array than a hash map sized to however many orders are actually live at once. tested that directly — same workload, one run with a tight, exactly-sized array, one run with the oversized one the real benchmark uses — and the difference was nothing, no consistent direction at all across five passes. wrong guess, at least it was cheap to rule out.

the real answer was sitting in data i already had. that percentage is a fraction of the total cycle count, and the total cycle count for this version had just collapsed everywhere. multiply the percentage back against its own workload's total cycles and the *absolute* cost in that category had gone down in every single case — down over a third for random prices. the fraction only went up because everything around it got so much cheaper that the one thing that didn't shrink took up more of a much smaller pie. not new cost. just the same fixed cost, standing out more once the rest of the work stopped hiding it.

the ratio i'd been tracking since the earliest baseline — same-price throughput divided by random-price throughput, 1.7-ish for two versions, then 1.195 after the array, measured fresh again right before this change at 1.204 — closed to **1.086**. four versions in, the two workloads that started nearly twice as far apart as they could be now sit within a tenth of each other.

## the test i wrote knowing it couldn't fail

by the fourth version, the differential harness from a few sections back had been run so many times it stopped feeling like a safety net and started feeling like a formality — which is exactly the moment it's worth double-checking whether it's still earning its keep or just running out of habit.

the honest answer is that it had picked up a real blind spot along the way. every one of those runs replays a randomly generated sequence of inserts and cancels, and random generation, left alone, tends toward the boring middle of its own distribution — plenty of variety in price and timing, but nothing that deliberately goes looking for the exact scenario where two implementations are most likely to disagree. so alongside the random workload, there's a second, deliberately adversarial one: every single order lands at the exact same price, on purpose, because that's precisely where an intrusive list and a flat array's internals diverge from each other the hardest. correctness matters most exactly where the implementations are least alike under the hood, and a purely random generator will happen upon that case eventually, maybe, if you're patient. the adversarial one puts it in front of the test on the first run, every time.

worth showing the actual comparison, since "the ledgers matched" undersells what's being checked:

```cpp
bool tradesEqual(const Trade& a, const Trade& b) {
    return a.makerOrderId == b.makerOrderId && a.takerOrderId == b.takerOrderId &&
           a.price == b.price && a.quantity == b.quantity;
}
```

every field of every trade, in order, across a run that can be hundreds of thousands of actions long. one mismatched quantity on trade number 40,000 fails the whole comparison, and the failure message points at exactly that trade, not just "something's different somewhere."

by the time version four existed, i had seven of these tests — harness sanity-check, then two per version against the baseline, random and adversarial. all pairwise-consistent by construction: if version two matches the baseline and version three matches the baseline, they already agree with each other, transitively, without anyone needing to check. so i wrote an eighth test anyway, one shared workload run through all four at once, that doesn't prove anything the other seven didn't already prove. i wrote it because "provably implied by seven other tests" and "stated once, plainly, as a closing fact" aren't actually the same kind of useful — the second one is what you'd point at if someone asked "so do all four really agree?" instead of handing them seven test names and the transitivity argument.

## four versions, one table

everything above, side by side, measured back to back in one run so the numbers are actually comparable to each other and not stitched together from four separate days. throughput is in millions of actions (inserts and cancels combined) per second:

| workload | v1 | v2 | v3 | v4 | total |
|---|---|---|---|---|---|
| random prices | 3.13 m/s | 4.35 m/s | 5.55 m/s | 12.33 m/s | +294% |
| heavy cancels | 4.23 m/s | 5.96 m/s | 7.37 m/s | 14.52 m/s | +243% |
| same price | 5.38 m/s | 6.75 m/s | 6.68 m/s | 13.39 m/s | +149% |

three to four times faster than where this started, depending on which workload you look at. and underneath that headline number, three separate, independently-measured reasons for it: heap allocation was worth roughly a third of total time, uniformly, but wasn't the reason one workload beat another. tree traversal was the biggest single piece of that gap, closing it most of the way. lookup-structure shape for cancellation closed most of what was left. none of those three answers were visible from a single "before and after" number — they only came apart because there were four separate, verified implementations to compare instead of one.

## auditing it a second time, after it was already "done"

the table above felt like an ending. it wasn't, quite — before actually calling any of this finished, i went back and asked the same question the very first audit asked, months earlier: if i didn't trust this code, what would i go looking for.

the coverage number said 99.2% line coverage, and it was tempting to just believe that meant "tested." it doesn't mean that. it means those lines executed at some point during some test — not that anyone deliberately checked the behavior on that line was correct. two real gaps were hiding behind a number that looked complete: cancelling an order id that was never inserted at all, on a book that already has other orders resting in it, and — the one i actually like finding — whether a price level, once its last order cancels or fills away, gets *erased* from the book's map or just left sitting there, empty, forever. nothing in the public interface behaves differently either way. an empty, un-erased price level is silently harmless to every trade the engine will ever produce. it would just sit there, taking up space, for the entire life of the process — the kind of leak that never shows up as a wrong answer, only as a process that mysteriously uses more memory the longer it runs. i had the exact accessor needed to check this directly (added months earlier for a completely different test), and had simply never pointed it at this specific question. twelve new tests later, both gaps were closed, across every version — not because coverage demanded it, coverage was already "good enough" — because being asked directly "is this actually checked" and coverage's own definition of "checked" turned out to be two different claims.

the second thing was smaller in code but bigger in what it revealed: `clang-tidy` had been sitting in the ci pipeline this whole time, non-blocking, and had never once run on this machine — no llvm installed, a gap the ci writeup itself admitted honestly rather than pretended around. installed it. ran it for the first time. got two hard errors immediately, and for a second they looked exactly like real bugs — until the actual message turned out to be about missing standard-library headers, not missing code. two different clang installs on the same machine, disagreeing about where the standard library lives, is not a code problem, and figuring that out cost more time than fixing it did. once that was sorted: forty-four warnings about headers being used without being directly included — relying on some other header to drag them in as a side effect, which works fine until that other header ever changes what *it* includes, and then everything downstream breaks for a reason that has nothing to do with the code that actually broke. fixed all forty-four. one of them was a genuinely unused `#include` that had been sitting there the whole time, doing nothing. and past that: nothing. no dead code. no unused variables. no unreachable branches. a real, checked "clean" instead of an assumed one — which only means something because the check that produced it had never actually run before.

## the actual thing i'd tell someone about this project

the two moments that taught me the most weren't the wins.

one was the audit — going back through code that already had a green test suite and asking it to prove itself again, harder, on purpose. the tests weren't lying. they just weren't asking the right questions yet. a reused order id and a negative number handed to `std::stoull` were both sitting there the whole time, both silent, both the kind of bug that never announces itself until something downstream is already wrong and nobody can say exactly when it started being wrong.

the other was the ten percent. the sentence at the very top of this post — the one about making something slower on purpose, or at least keeping the number once it happened instead of hiding it — is describing that regression, and i'm glad i wrote it up the way i did instead of quietly patching it before publishing anything. because a version later, the exact same measurement that made version three look worse is what pointed straight at the fix, and the fix turned that same workload into the biggest turnaround of the entire project — a real regression flipped into one of its strongest results. if i'd smoothed the number over the first time, i'd have gotten to the same fix eventually, probably. but i wouldn't have had the paper trail that made it obvious *why* it worked, and i wouldn't have trusted the fix nearly as much when it landed.

four versions of this order book later, that's the pattern i keep landing back on: the measurement you don't like is usually the one worth writing down most carefully, because it's the one still pointing at something true.
